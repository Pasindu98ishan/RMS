# ADR-007: Catalog, floor and import choices (M1.1)

**Status:** Accepted · 2026-11-22 · Contract `docs/api/openapi.yaml` v0.2.0 · Scope in `docs/requirements/m1.1-scope.md`

## Context
M1.1 adds kitchen stations, categories, menu items with two price lists, modifier groups, tables with a floor plan, delivery areas, reason lists and a spreadsheet import. The scope note fixes most rules; these are the choices it leaves open or that came out of building it.

## Decision
1. **Nothing is deleted, only deactivated** (items, categories, groups, tables, areas, reasons, stations). `active` is a field of the create and update bodies (PUT is a full replacement), not a separate action. A station with active items cannot be deactivated (409 `STATION_IN_USE`).
2. **One read for the order screen.** `GET /menu/pos` returns every sellable thing in one call (categories with items, active modifier groups, active stations); the POS searches it locally and reloads it at login and now and then. There is no STOMP event for menu changes in M1.1 (lead decision); real-time comes with M1.2.
3. **Sold out is not an edit.** `available` is excluded from optimistic locking and from `UPDATE` statements the item form issues (`@OptimisticLock(excluded = true)`, `@DynamicUpdate`). A cashier's toggle never bumps the item's `version`, so an admin's open form still saves, and the form's save never brings a sold-out item back. The daily reset is a plain bulk update for the same reason.
4. **Daily sold-out reset** runs once a minute and at start-up, keyed on the business date (calendar date in Asia/Colombo, shifted by the business-day start time). The last reset date is kept in a `setting` row (`availability_reset`), so a restart or a second run the same day does nothing. The switch (`resetAvailabilityDaily`, on by default) lives in the `menu` setting. The day is remembered even when the reset is off, so switching it on later in the day does not wipe that day's sold-out marks.
5. **Modifier groups** gained an `active` flag (not in the original data model). Options keep their identity through their `id`; options missing from an update are removed. Rules: required means minimum 1, optional means minimum 0, maximum between the minimum (and 1) and the number of options, price deltas not negative, option names unique inside the group. The import uses the same rules.
6. **Money in requests** is the `Money` string with exactly 2 decimals (ADR-006 decision 12) and not negative for prices, fees and deltas. The import is more forgiving because spreadsheets are: it accepts 0 to 2 decimals ("150", "300.5") and normalises them.
7. **Terminals** keep the field names `kitchenStationId` / `orderingPointId`. KITCHEN needs an active station; an unknown station or ordering point is 422. The foreign keys are added `NOT VALID`, so terminals registered before M1.1 are not re-checked. The unregistered setup screen reads its choices with `POST /terminals/setup-options` (owner credentials in the body, same per-IP limit as registration), because it has no token.
8. **Floor plan** x / y are the table's centre on a 1000 x 700 grid. Positions are saved in bulk, all or nothing, each with the table's `version`. A new table without a position takes the next free slot of a 120-unit grid.
9. **Import**
   - **File reading:** one first sheet of a CSV (UTF-8 with or without BOM, comma or semicolon) or an XLSX file, 5 MB and 5000 rows at most. The row number in an error is the spreadsheet row (empty lines count, the header is row 1). Unknown or duplicate columns are errors, so a typo in an optional column cannot silently drop data.
   - **Report and result:** the result is always a 200 report with `ok`; 422 `IMPORT_FILE_INVALID` is only for a file that cannot be read.
   - **Matching:** rows match existing records by key (categories by name, items by code, groups by name, tables by number) and update them. A blank or absent optional cell clears the value on a re-import (a blank `foreign_price` removes it); `active` and table positions are kept when absent.
   - **All or nothing, in two layers:** the file module type-checks cells and reports parse errors; the owning module then checks the parsed rows against each other and the existing data and applies them. All errors are collected before anything is saved. Rows with a parse error are left out of the second check, so a file can need two passes.
   - **Dry run:** a dry run does every check and computes the exact counts from the same in-memory comparison as the real import, but writes nothing and no audit row. (Modifier groups, which are few, still go through the group service and are rolled back.)
   - **Linear time (BUG-1-008):** the import services load the lookup data (categories, stations, groups, existing items or tables) once into maps and never call the one-record services per row (those reload lookups and flush per call, which made 5000 rows take about 190 s). New rows are saved without a flush, Hibernate sends them in JDBC batches, and one flush plus one batch of audit rows ends the import. `MenuItem.available` is `updatable = false` (it is changed only by the bulk UPDATE of the sold-out toggle) instead of using `@DynamicUpdate`, because dynamic updates cannot be batched.
10. **Dev sample data** is created only when missing and never changes existing records, so a developer's edits survive a restart. It goes through the import services, so it is also a test of them.
11. **Module boundaries.** `menu`, `floor` and `dataimport` follow ADR-001: other modules see only plain records from the `service` package (`StationInfo`, `OrderingPointInfo`, `ImportCounts`), never entities or repositories. An ArchUnit test enforces it.

## Consequences
- `data-model.md` should list `modifier_group.active`, `ordering_point.sort_order` and the settings keys `menu` and `availability_reset`.
- The frontend refreshes `/menu/pos` periodically instead of subscribing to menu events.
- A partial re-import can clear optional values (see 9). The Import screen should say so next to the template download.
- Migration V7 makes the unique (item, group) constraint of `menu_item_modifier_group` DEFERRABLE INITIALLY DEFERRED. Hibernate rewrites an `@OrderColumn` list in place, so reordering an item's groups briefly puts the same group at two positions inside the transaction; the check now runs at commit, where the final state is always unique (BUG-1-007).
